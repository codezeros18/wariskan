# Wariskan — Webhook Security Checklist

Covers the Meta (WhatsApp Cloud API) integration specifically.
Intended for hackathon submission review and handoff to production ops.

---

## Required Meta App Settings

In [Meta Developer Console](https://developers.facebook.com/apps/) → your app:

| Setting | Value | Why |
|---|---|---|
| Webhook URL | `https://your-n8n-host/webhook/whatsapp-messages` | Must be HTTPS |
| Verify Token | Match `WHATSAPP_VERIFY_TOKEN` in `.env` | Used in GET challenge |
| Subscriptions | `messages` only | Least privilege |
| App Secret | Generated by Meta — copy to `META_APP_SECRET` | Signs every POST |
| App Mode | Production (not Development) | Dev mode limits recipient phones |

**Never expose your App Secret or Permanent Token in client-side code, logs, or public repos.**

---

## Environment Variables — Security Classification

| Variable | Classification | Rotation frequency |
|---|---|---|
| `META_APP_SECRET` | Secret | If exposed: rotate immediately |
| `WHATSAPP_TOKEN` | Secret | Every 60 days or if exposed |
| `WHATSAPP_VERIFY_TOKEN` | Secret | If webhook URL exposed |
| `SUPABASE_SERVICE_KEY` | Secret | If exposed: rotate immediately |
| `WHATSAPP_PHONE_NUMBER_ID` | Internal | No rotation needed |

## If Your Webhook URL Is Leaked

A leaked URL means an attacker can send fake webhooks. Do this in order:

1. **Immediately** rotate `WHATSAPP_VERIFY_TOKEN` in both `.env` and Meta Console → Webhooks → Edit
2. Confirm `META_APP_SECRET` is set — signature validation will reject spoofed requests even with the correct URL
3. Check `incoming_messages` in Supabase for unusual `phone_from` values or spikes in volume
4. If you see spoofed messages were processed: audit affected `transactions` rows and mark as `dibatalkan`

**Risk with META_APP_SECRET set:** Low — forged requests fail HMAC validation.  
**Risk without META_APP_SECRET set:** High — anyone with the URL can inject transactions.

---

## If Your App Secret Is Leaked

1. Go to Meta Developer Console → App Settings → Basic → **Reset App Secret**
2. Update `META_APP_SECRET` in `.env` (and Railway/Render/wherever you deploy)
3. Restart the scheduler and n8n
4. Audit `incoming_messages` for the past 24 hours for anomalies

---

## If Your WhatsApp Permanent Token Is Leaked

1. Go to Meta Developer Console → WhatsApp → API Setup → **Regenerate** the token
2. Update `WHATSAPP_TOKEN` in `.env`
3. Restart n8n (cached env vars won't update until restart)
4. Check `outgoing_messages` in Supabase for messages you didn't send

## Deployment Hardening Checklist

### Before submitting / going live

- [ ] `META_APP_SECRET` is set in production env (enables HMAC validation)
- [ ] `WHATSAPP_MOCK_MODE` is `false` in production env
- [ ] `.env` is in `.gitignore` — confirm with `git status`
- [ ] `service-account-key.json` is in `.gitignore`
- [ ] Supabase RLS is enabled on all tables (already set in `001_initial_schema.sql`)
- [ ] n8n is behind HTTPS (Railway/Render provide this automatically)
- [ ] n8n admin panel is password-protected (`N8N_BASIC_AUTH_ACTIVE=true`)
- [ ] Scheduler HTTP server is not exposed to the public internet (only n8n calls it internally)
- [ ] `SCHEDULER_API_KEY` is set if the scheduler port is reachable externally

### Rate limiting in place

- [ ] `WH_RATE_LIMIT_PER_MIN=30` set (30 inbound messages/minute per user)
- [ ] `WHATSAPP_RATE_LIMIT_PER_SEC=20` set (20 outbound messages/second)
- [ ] WhatsApp mock mode disabled in prod (`WHATSAPP_MOCK_MODE=false`)

### Monitoring

- [ ] `SLACK_ERROR_WEBHOOK` set — scheduler and helper errors will notify Slack
- [ ] Supabase `incoming_messages` table accessible for manual audit
- [ ] Supabase `outgoing_messages` table accessible for delivery audit

## What Signature Validation Protects Against

The `validateSignature()` function in `webhookSecurity.js` uses HMAC-SHA256
with your App Secret to verify that each POST request genuinely came from Meta.

**Without it:** anyone who discovers your webhook URL can send fake transactions.  
**With it:** forged requests are rejected at the first line of processing.

The implementation uses `crypto.timingSafeEqual()` (constant-time comparison)
to prevent timing oracle attacks where an attacker could infer the correct HMAC
byte-by-byte by measuring response latency.

---

## n8n-Specific Notes

- The Webhook node should have **"Raw Body"** enabled for exact HMAC validation.
  Without it, the code node re-stringifies the parsed JSON — close but not byte-exact.
  This is acceptable for the hackathon; for production, enable raw body.
  
- The `responseMode: "onReceived"` setting on the POST webhook node sends HTTP 200
  immediately before processing completes. This prevents Meta from retrying
  (Meta retries if it doesn't get 200 within ~20 seconds).

- Webhook URLs in n8n include a random UUID path segment, which provides
  obscurity (not security) by default. Still set `META_APP_SECRET`.
